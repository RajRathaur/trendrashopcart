# Project Rules

- Validate delivery phone, address, and compulsory GPS coordinates through `src/lib/deliveryDetails.ts` before every customer order insert, so all checkout paths enforce the same rules.
- Festival sale settings (on/off, title, coupon, start/end time) live in site_content keys parsed by src/lib/festivalSale.ts, so admin can change them without code changes.
- Virtual Try-On runs fully in the browser (MediaPipe Pose body landmarks only, loaded lazily from CDN; fit math in `src/lib/tryOnFit.ts`, garment cut-out in `src/lib/garmentCutout.ts`), so shopper camera/photos never leave the device and the product page bundle stays light. The only exception is the opt-in AI Pro Try-On (`ai-tryon` edge function): it takes the garment photo from the product record, never stores the shopper photo, and enforces a per-user daily cap via `ai_tryon_usage` with rules in `supabase/functions/ai-tryon/limit.ts`.
- Razorpay amounts are decided only in `create-razorpay-order` (shop order = DB order total minus a server-revalidated coupon; coins = fixed packs), and `verify-razorpay-payment` confirms only Razorpay orders whose notes bind them to that user and order, so a client can never choose what it pays.
- Scheduled backend jobs authenticate to edge functions with a per-job token from the RLS-locked `internal_job_tokens` table (sent as `x-job-token`), because the cron job only has the public anon key.
- Which pages open without login is decided only by `src/lib/publicPaths.ts` (used by `AuthGate`), and product-page buttons send logged-out shoppers to `loginPath(...)` so they return to the same product after login.
- The store's main address lives only in `src/lib/site.ts` (`SITE_URL`) and must match `index.html`, `public/robots.txt` and `public/sitemap.xml`, so Google treats the custom domain, not the lovable.app address, as canonical. `public/sitemap.xml` is rewritten by `scripts/generate-sitemap.ts` before every dev/build run (public pages + active products from the database), so edit that script, never the XML by hand.
- Trendra Bazaar (used-item classifieds) rules live in the database: `bazaar_listing_guard` forces new/edited ads to `pending` until an admin approves, and chat rows are fixed up by `bazaar_conversation_guard`/`bazaar_message_after_insert`, so the client can never self-approve or spoof a chat partner. Pages are lazy-loaded under `/bazaar`; only `/bazaar` and `/bazaar/item/:id` are public.
- Trendra Reels rules live in database guards and counter triggers; reel files use `product-images/reels/<user_id>/`. Watching is public, but profiles, username search and posting require login because social data is authenticated-only.
- Technical videos use `product-images/videos/<user_id>/` and database approval/view guards; creator earnings come only from `creator_balances`, and payouts record manually completed transfers, never send money. This keeps moderation and financial totals server-controlled.
- Video marketing uses protected campaign RPCs and server-priced packs; captured Razorpay payments must match purpose, owner, campaign and amount before approval can start timed placement. Campaign metrics count unique signed-in non-owner events per day, so public viewing does not collect visitor identifiers.
